# 1.0 神器使隔离技术原型执行计划

## 1. 文档目的

本文仅记录八名普通规模神器使未来可能采用的隔离技术原型顺序，并定义预备性的技术底座、阶段门禁和验收方式。

当前项目仍处于 1.0 背景、角色与设计准备阶段。本文已经冻结，不是当前实施计划，也不授权创建实施卡、测试骨架、原型文件、正式数值、正式收益、最终事件文本、图标、美术或可发布脚本。只有用户以后明确宣布进入技术原型阶段，本文才可重新提交审核。

安托涅瓦继续使用多职业专项原型；爱缪莎继续使用主线、危机、旗舰与终局锚点专项蓝图，不进入本执行计划。

## 3. 共用技术底座

### 3.1 国家层权威账本

每名角色使用独立命名空间保存：

- 唯一人物存在状态。
- 当前机制阶段。
- 当前对象类别与可恢复引用。
- 已执行步骤与幂等标记。
- 暂停、失败、清理和冷却状态。
- 职业切换前后的连续性信息。

角色之间不得共享同一阶段变量、对象槽或冷却，避免一个原型污染另一个原型。

### 3.2 同一领袖实体职业切换

先只验证通用流程：

1. 验证目标领袖唯一且有效。
2. 安全卸任不兼容岗位。
3. 修改同一人物的职业。
4. 清理不兼容职业特质。
5. 保留等级、人物身份、关系与角色机制账本。
6. 由玩家重新指派岗位。
7. 再次切换时不复制角色、奖励或冷却。

若 Stellaris 4.4.3 无法稳定保留同一实体，立即停止该路线并形成失败报告；不得自行改用删除并重建领袖。

### 3.3 对象验证与清理

所有对象引用必须具备：

- 首次登记验证。
- 每次关键推进前验证。
- 所有权改变验证。
- 对象销毁或失效清理。
- 存档读取后的重新验证。
- 重复事件和脉冲幂等保护。

目标对象只保存临时参与标记；国家账本是恢复与清理依据。

### 3.4 调试入口

隔离原型只允许使用明确标注为测试用途的入口，并满足：

- 默认不向普通玩家显示。
- 不依赖正式科技、传统、飞升或白夜馆流程。
- 能逐阶段推进、制造目标失效、切换职业和执行清理。
- 调试文本明确显示当前阶段与对象验证结果。
- 原型完成后能够完整移除，不污染发布入口。

### 3.5 原型数据禁区

隔离原型不得：

- 提供正式资源、人口、科技、舰船、建筑或战斗收益。
- 使用最终本地化、图标和剧情文本冒充成品。
- 写入爱缪莎主线、天灾、命运规则或安托涅瓦专项状态。
- 修改原版文件或覆盖其他 Mod 对象。
- 通过每日或月度全银河扫描维持状态。

## 4. 推荐执行顺序

### 第 0 阶段：共用测试骨架

目标：验证独立命名空间、国家账本、唯一领袖查找、调试入口、对象验证、存读档和幂等。

本阶段不实现任何角色机制，只建立最小测试合同。骨架通过后才能开始角色原型。

### 第 1 阶段：晏华——态势研判

优先原因：

- 三阶段单目标账本最适合验证国家层权威状态。
- 可以同时验证第一套行政官／指挥官同实体切换。
- 不需要战斗监听、资源收益或复杂对象并发。

通过门槛：唯一晏华、双职业往返、三阶段推进、目标失效、死亡／解雇、存读档、重复触发均稳定。

### 第 2 阶段：安——时序学习

复用内容：国家账本、职业切换、对象清理。

新增验证：记录、经验、一次应用与事前紧急保护；必须证明不会恢复已销毁对象或复制历史结果。

### 第 3 阶段：幽桐——自定射界

复用内容：国家账本、唯一领袖、对象验证。

新增验证：舰队绑定、同星系目标、校准、越界请求、恢复期，以及舰队合并／拆分／销毁后的防复制清理。

### 第 4 阶段：拉比——阿米特的守则

复用内容：幽桐的舰队与目标生命周期。

新增验证：受控威胁登记、先保护后有限反击、撤离／恢复；不监听全银河战斗，不建立善恶审判。

### 第 5 阶段：赛斯——愿望履责

复用内容：国家账本、职业切换、暂停与恢复。

新增验证：普通事项与紧急救援共用一条队列、原事项暂停／恢复、现实后果结算和冷却。

### 第 6 阶段：格蕾莎——生命档案

复用内容：单队列、双职业、对象清理、分支状态。

新增验证：殖民地／舰队病例类型、取样、应急处置或继续分析、知情同意与违规记录。

### 第 7 阶段：雯梓——经纬共局

复用内容：殖民地／舰队双对象类型、双职业、分支账本。

新增验证：共同目标、保护边界、黑白行动、失衡、主动收官和受影响对象的拒绝／离开边界。

### 第 8 阶段：丽——责任投资

最后执行原因：

- 需要行政官／科学家／指挥官三职业切换。
- 同时覆盖殖民地、舰队和虚拟工程项目三种对象。
- 包含成本、风险、协商、履约、兑现、止损与审计，状态最复杂。

通过门槛：三职业共享同一项目账本，不复制投入、不清除风险、不重复结算；科学家路径只覆盖工程应用。

## 5. 每阶段统一验收矩阵

每个角色原型必须逐项记录：

- [ ] 新开局能够创建或定位唯一测试领袖。
- [ ] 重复入口不会复制领袖或机制账本。
- [ ] 启动、推进、暂停、恢复、完成、取消和失败状态正确。
- [ ] 目标销毁、所有权改变或失效后能够清理。
- [ ] 领袖换岗、受伤、失联、死亡和解雇按责任卡处理。
- [ ] 需要切换职业的角色往返切换后仍是同一人物。
- [ ] 存档读取后阶段、目标与冷却一致。
- [ ] 重复事件、每日／月度脉冲不重复结算。
- [ ] 原型没有正式资源、人口、舰船、建筑、科技或战斗收益。
- [ ] `error.log` 没有该原型的作用域、无效对象、重复定义或本地化硬错误。

## 6. 阶段失败处理

- 共用骨架失败：停止全部角色原型，不并行绕过。
- 同一领袖职业切换失败：记录失败证据并回到人工审核，不自行采用删除重建。
- 舰队对象生命周期失败：停止幽桐与拉比原型，不用常驻全局修正替代。
- 对象清理或幂等失败：当前角色不得进入下一阶段。
- 正式效果无法实现：只提交可行性报告，不以相似但越界的机制替代。
- 任一降级方案都必须重新获得人工批准。

## 7. 建议文件边界

原型阶段建议单独使用测试文件，不改动现有正式角色事件：

- `events/aemod_character_prototype_events.txt`
- `common/scripted_effects/aemod_character_prototype_effects.txt`
- `common/scripted_triggers/aemod_character_prototype_triggers.txt`
- `localisation/simp_chinese/aemod_character_prototype_l_simp_chinese.yml`
- `reports/character_prototype_test_report.md`

以上只是拟定边界，获得本计划批准前不创建。测试入口和正式实现必须分离；正式实现不得直接复制带有测试 flag、调试选项或虚拟对象的原型文件。
