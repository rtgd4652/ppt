# 1. 文档目的

本蓝图把已经批准的旗舰职责转换为可验证的 Stellaris 4.4.3 技术问题，并定义隔离原型的文件边界、测试顺序、故障注入和验收证据。

本文件不编写正式 Mod 脚本，不确定正式舰名、模型、武器槽、数值或美术，也不自动开放隔离原型闸门。

# 2. 冻结的上游约束

本蓝图必须服从：

- [专属旗舰机制职责卡](aemusa_fate_stabilization_flagship_responsibility_card_v1.0.md)。
- `FSR-001`：文明完成一次正式建造，同一时间只存在一个永久身份。
- `FSR-002`：爱缪莎保持独立领袖身份，旗舰现场逐锚恒定，一次只处理一个锚点。
- `FSR-003`：旗舰是独立单舰编队的终局主力战舰，不与普通舰队合并。
- `FSR-004`：真正摧毁后立即在合法首都满状态重现，爱缪莎不会死亡。
- `FSR-005`：事件驱动永久账本、幂等重现和轻量读档审计，不使用月度全局轮询。
- 1.0 暂不处理多人继承与跨国移交。

# 3. 技术事实与不可假定事项

## 3.1 原则上低风险

- country flag 与运行时变量可以保存路线国家的生命周期状态。
- 舰船、舰队和国家事件可以承载局部对象检查与状态转换。
- 首都、舰队、舰船和领袖是不同作用域，所有效果必须显式切换并检查对象存在。
- 使用独立 scripted trigger 与 scripted effect 可以集中唯一性和状态转换逻辑。
- 事件驱动检查比每月遍历所有国家和舰队更符合性能边界。

## 3.2 必须通过原型验证

- 何种 on_action 或事件链能够稳定区分“真正摧毁”与紧急撤退、失联、跃迁和事件隐藏。
- 摧毁事件中可用的 ship、fleet、owner 与攻击者作用域及其存活时间。
- 立即在首都生成替代舰时，旧舰死亡事件是否可能重入或触发第二次重现。
- 固定设计生成后能否保证必需部件完整、可跃迁、可作战并保持独立编队。
- 玩家能否通过舰队管理器、合并命令、升级、自动设计或控制台制造第二个合法对象。
- 读档后如何区分短暂找不到对象与真正缺失，而不依赖月度扫描。
- 部署期间如何可靠限制跃迁、撤退和任务切换，同时允许需要的战斗行为。
- 爱缪莎处于不同职业、通讯、事件或暂时不可用状态时，参与条件能否稳定求值。

## 3.3 当前不得宣称可行

- 不宣称能让已经被摧毁的同一个引擎舰船对象原地复活；职责中的“永久身份”由国家账本承载，物质舰体可以是新对象。
- 不宣称仅凭舰船尺寸定义就能永久禁止所有 UI 合并路径。
- 不宣称舰船事件在所有撤退、失踪与销毁路径上提供完全相同的作用域。
- 不宣称瞬时重现不会造成镜头、舰队选择、战斗结算或通知异常。
- 不宣称旧版舰船脚本、旧 Stage 9 模型或旧设计能直接作为测试基线。

# 4. 隔离原则

- 原型不得直接写入正式 `mod/` 内容目录。
- 原型文件应先位于仓库的独立测试区，由明确步骤组装为临时本地测试 Mod。
- 所有原型 key、namespace、flag、变量与本地化使用专属前缀，禁止与正式 `aemusa`、现有 `destiny_lord` 或其他内容共用身份键。
- 原型只能通过明确的开发测试入口启动，不能注册为普通新开局自动事件。
- 原型不引用正式美术、旧模型、正式科技树、白夜馆招募或 1.0 主线进度。
- 删除整个原型目录后，正式 Mod 工作树和存档设计不应受到影响。
- 每轮原型测试必须记录游戏版本、启用 Mod、步骤、预期、实际结果和相关 `error.log` 片段。

# 5. 建议的隔离结构

本节只是目录合同，不表示现在创建原型代码：

```text
tools/prototypes/aemusa_flagship/
├── README.md
├── prototype_manifest.md
├── mod_skeleton/
│   ├── common/
│   ├── events/
│   ├── localisation/
│   └── descriptor.mod.example
├── test_cases/
└── reports/
```

- `mod_skeleton/` 只保存可复制到临时测试 Mod 的源文件。
- `descriptor.mod.example` 不直接覆盖玩家现有本地 Mod 描述文件。
- 测试生成物、游戏日志和临时二进制资产默认不进入 Git。

# 6. 原型通过顺序

原型必须按以下顺序逐层通过，失败时不得跳到下一层：

1. 独立测试舰能够由固定入口生成、跃迁、交战和被摧毁。
2. 国家账本只允许首次生成一个正式身份。
3. 真正摧毁能够触发一次且仅一次的首都满状态重现。
4. 紧急撤退、跃迁、失联和读档不会误触发重现。
5. 舰队合并、拆分、升级和重复入口不能生成第二个合法身份。
6. 部署锁定可以阻止离场，并在中断后保持幂等。
7. 爱缪莎参与条件能够在不改变领袖职业的情况下控制部署入口。
8. 新开局、战斗中存档、摧毁帧附近读档与迁都后摧毁均通过。

# 7. 性能预算

- 正常运行不得使用每月 `every_country`、`every_owned_fleet` 或全银河舰船扫描。
- 常驻状态只保存少量国家 flag、变量和必要对象标记。
- 一致性审计只在首次建造、确认摧毁、重现完成、明确读档恢复入口和开发命令中运行。
- 对象检索优先限定路线国家和正式身份标记，不把普通同级舰船纳入候选。
- 性能验收不仅记录平均帧率，还要检查月结尖峰、事件重复次数和存档体积变化。

# 9. TFR-001：隔离原型位置、命名空间与装载方式

## 9.1 方案 A：仓库外层测试骨架，手动组装临时 Mod（推荐）

- 原型源文件放在 `tools/prototypes/aemusa_flagship/mod_skeleton/`，不会被正式 Mod 加载。
- 测试时由明确的构建或复制步骤组装到独立临时 Mod 目录，不覆盖 `mod/descriptor.mod`。
- 使用独立 namespace 和统一前缀，例如 `aemusa_flagship_proto` 与 `aemusa_fp_*`；正式实现不得直接沿用测试 key。
- 只提供开发事件或控制台入口，不注册普通开局、月度脉冲或正式科技解锁。
- 测试报告和原型源文件可以进入 Git；本地临时 Mod、日志、存档和二进制生成物不进入 Git。

优势：原型默认完全不加载，最不容易污染正式 Mod、正式存档和现有舰船定义；失败时可整体删除。

风险：每次测试前需要执行一次明确的组装步骤，必须避免测试人员误把临时 Mod 当作正式版本发布。

## 9.2 方案 B：原型文件放入正式 Mod，但用隐藏触发器关闭

原型定义直接放入 `mod/`，正常情况下依靠永假触发器或调试 flag 隐藏。

优势：无需单独组装测试 Mod，修改后可直接启动游戏验证。

风险：即使事件不触发，舰船尺寸、设计、部件和本地化仍可能被加载；命名冲突、错误日志和发布污染风险较高。

## 9.3 方案 C：直接复用现有正式舰船脚本作为原型

在当前专属舰脚本上逐步加入账本、重现和独立编队逻辑。

优势：最快看到游戏内效果，也能复用现有舰船资源。

风险：旧舰名、旧模型、旧超规格槽位和历史兼容问题会混入验证结果，无法证明新职责本身是否可行，也违反已批准的隔离要求。

## 9.4 当前建议

建议批准方案 A。技术原型首先要保证“失败可以完整撤销”，其次才是启动方便。独立骨架还能强制我们为每个测试列出依赖，而不是继续依赖当前正式 Mod 中尚未清理的旧舰船实现。

## 9.5 审核结论

- 决定：批准方案 A“仓库外层测试骨架，手动组装临时 Mod”。
- 原型源文件位置锁定为 `tools/prototypes/aemusa_flagship/`，不得直接写入正式 `mod/`。
- 原型通过独立临时 Mod 装载，不覆盖正式 `descriptor.mod`，也不依赖正式舰船、科技、主线或美术资源。
- 原型统一使用 `aemusa_flagship_proto` namespace 与 `aemusa_fp_*` 测试前缀；正式实现不得直接沿用测试 key。
- 原型只提供明确的开发事件或控制台入口，不注册普通开局、月度脉冲或正式科技触发。
- 可提交 Git 的范围为原型源文件、说明、测试用例和报告；临时 Mod、存档、日志及二进制生成物不进入 Git。
- 本批准只确定隔离合同，不创建原型目录或脚本，隔离原型闸门继续关闭。
- 批准日期：2026-08-01。

# 10. TFR-002：生命周期账本到脚本状态的映射

本审核项决定国家、舰船和一次性事件分别保存什么状态。目标是让“同一永久身份”不依赖某一个会在摧毁时消失的舰船对象，同时避免多个 flag 互相矛盾。

## 10.1 方案 A：国家数值主状态＋永久里程碑＋舰船身份标记（推荐）

### 10.1.1 国家主状态

- 路线所属国家保存一个权威生命周期变量，原型暂用 `aemusa_fp_lifecycle`。
- 状态枚举建议为：
  - `0`：未解锁。
  - `10`：已解锁、可首次建造。
  - `20`：首次建造处理中。
  - `30`：正式旗舰现役。
  - `40`：已确认摧毁、等待本次重现处理。
  - `50`：重现事件处理中。
- 重现成功后回到 `30`；不额外设置一个长期“重现后现役”状态，避免现役被拆成多个等价分支。
- 任何状态变化都必须经过集中 scripted effect 或等价单一入口；普通事件不能任意改写变量。

### 10.1.2 永久里程碑

- 使用独立永久 country flag 记录“首次正式建造已经完成”，不能因舰船摧毁而清除。
- 使用单独变量保存最近一次确认摧毁序号和最近一次完成重现序号；二者相等表示当前摧毁已经处理。
- 主线阶段、原版天灾完成、旗舰建造资格和舰船生命周期分别记录，不把所有含义塞进同一个 flag。
- 奖励、通讯和教程节点使用各自的一次性里程碑，不能只根据现役舰船是否存在重复触发。

### 10.1.3 舰船与舰队对象标记

- 正式物质舰体保存一个 ship flag，表示它是当前永久身份的合法载体。
- 独立舰队可以保存辅助 fleet flag，用于 UI、合并审计和部署状态，但 fleet flag 不作为永久身份的唯一真相。
- 舰船和舰队对象被摧毁后可以消失；国家账本仍保留永久身份、摧毁序号和重现资格。
- 临时原型舰、旧测试舰、同舰种普通舰和视觉替代物不得携带正式身份标记。

### 10.1.4 一致性规则

- `lifecycle = 30` 时预期恰好存在一个合法 ship flag；找不到对象时先进入审计，不立即补舰。
- `lifecycle = 40` 且摧毁序号大于已处理序号时，允许进入一次重现处理。
- `lifecycle = 50` 时任何重复摧毁、读档恢复或调试入口都不得再次生成舰船。
- 重现舰生成并完成必需部件校验后，先记录已处理序号并切回 `30`，再显示通知。
- 若检测到两个合法对象，主线与奖励全部暂停，进入开发异常处理，不把两艘都当作现役。

优势：国家变量提供唯一权威状态，永久 flag 记录不可逆历史，舰船标记只确认当前载体；对象摧毁不会抹掉身份，也不会产生一组难以维护的互斥 flag。

风险：所有状态写入必须通过集中入口，否则数值状态与对象标记可能脱节；原型需要逐项测试非法跳转。

## 10.2 方案 B：每个阶段使用一个互斥 country flag

为未解锁、可建造、建造中、现役、摧毁和重现中分别设置 flag，切换时清除旧 flag、设置新 flag。

优势：脚本触发器直观，查看存档时容易辨认文字状态。

风险：事件中断后可能同时存在多个阶段 flag 或一个都没有；每增加状态都要修改所有清理分支，长期维护成本高。

## 10.3 方案 C：以保存的舰船或舰队 event target 为主状态

国家主要保存当前舰船或舰队 event target，通过目标是否存在判断现役与摧毁。

优势：能够直接定位当前对象，减少按标记搜索。

风险：舰船被摧毁后对象引用可能失效；仅凭引用不存在无法区分真正摧毁、撤退、隐藏和存读档边界，不适合作为永久身份账本。

## 10.4 当前建议

建议批准方案 A。永久身份属于国家级剧情账本，当前舰体只是该身份的载体。数值主状态负责互斥阶段，永久 flag 负责不可逆历史，ship/fleet flag 负责当前对象定位，三者职责分离最清楚。
