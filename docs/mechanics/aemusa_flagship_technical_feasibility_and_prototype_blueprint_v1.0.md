# 1. 文档目的

本蓝图把已经批准的旗舰职责转换为可验证的 Stellaris 4.4.3 技术问题，并定义隔离原型的文件边界、测试顺序、故障注入和验收证据。

本文件不编写正式 Mod 脚本，也不确定正式舰名、模型、武器槽、数值或美术；隔离原型闸门仅因 `TFR-007` 的明确人工批准而开放。

# 2. 冻结的上游约束

本蓝图必须服从：

- [专属旗舰机制职责卡](aemusa_fate_stabilization_flagship_responsibility_card_v1.0.md)。
- `FSR-001`：文明完成一次正式建造，同一时间只存在一个永久身份。
- `FSR-002`：爱缪莎保持独立领袖身份，旗舰现场逐锚恒定，一次只处理一个锚点。
- `FSR-003`：旗舰是独立单舰编队的终局主力战舰，不与普通舰队合并。
- `FSR-004`：真正摧毁后立即在合法首都满状态重现，爱缪莎不会死亡。
- `FSR-005`：事件驱动永久账本、幂等重现和轻量读档审计，不使用月度全局轮询。
- 1.0 暂不处理多人继承与跨国移交。

# 3. 技术事实与不可假定事项

## 3.1 原则上低风险

- country flag 与运行时变量可以保存路线国家的生命周期状态。
- 舰船、舰队和国家事件可以承载局部对象检查与状态转换。
- 首都、舰队、舰船和领袖是不同作用域，所有效果必须显式切换并检查对象存在。
- 使用独立 scripted trigger 与 scripted effect 可以集中唯一性和状态转换逻辑。
- 事件驱动检查比每月遍历所有国家和舰队更符合性能边界。

## 3.2 必须通过原型验证

- 何种 on_action 或事件链能够稳定区分“真正摧毁”与紧急撤退、失联、跃迁和事件隐藏。
- 摧毁事件中可用的 ship、fleet、owner 与攻击者作用域及其存活时间。
- 立即在首都生成替代舰时，旧舰死亡事件是否可能重入或触发第二次重现。
- 玩家可调整方案能否始终满足必需部件、跃迁与作战要求，并在首次生成和重现后保持独立编队。
- 玩家能否通过舰队管理器、合并命令、升级、自动设计或控制台制造第二个合法对象。
- 读档后如何区分短暂找不到对象与真正缺失，而不依赖月度扫描。
- 部署期间如何可靠限制跃迁、撤退和任务切换，同时允许需要的战斗行为。
- 爱缪莎处于不同职业、通讯、事件或暂时不可用状态时，参与条件能否稳定求值。

## 3.3 当前不得宣称可行

- 不宣称能让已经被摧毁的同一个引擎舰船对象原地复活；职责中的“永久身份”由国家账本承载，物质舰体可以是新对象。
- 不宣称仅凭舰船尺寸定义就能永久禁止所有 UI 合并路径。
- 不宣称舰船事件在所有撤退、失踪与销毁路径上提供完全相同的作用域。
- 不宣称瞬时重现不会造成镜头、舰队选择、战斗结算或通知异常。
- 不宣称旧版舰船脚本、旧 Stage 9 模型或旧设计能直接作为测试基线。

# 4. 隔离原则

- 原型不得直接写入正式 `mod/` 内容目录。
- 原型文件应先位于仓库的独立测试区，由明确步骤组装为临时本地测试 Mod。
- 所有原型 key、namespace、flag、变量与本地化使用专属前缀，禁止与正式 `aemusa`、现有 `destiny_lord` 或其他内容共用身份键。
- 原型只能通过明确的开发测试入口启动，不能注册为普通新开局自动事件。
- 原型不引用正式美术、旧模型、正式科技树、白夜馆招募或 1.0 主线进度。
- 删除整个原型目录后，正式 Mod 工作树和存档设计不应受到影响。
- 每轮原型测试必须记录游戏版本、启用 Mod、步骤、预期、实际结果和相关 `error.log` 片段。

# 5. 建议的隔离结构

本节只是目录合同，不表示现在创建原型代码：

```text
tools/prototypes/aemusa_flagship/
├── README.md
├── prototype_manifest.md
├── mod_skeleton/
│   ├── common/
│   ├── events/
│   ├── localisation/
│   └── descriptor.mod.example
├── test_cases/
└── reports/
```

- `mod_skeleton/` 只保存可复制到临时测试 Mod 的源文件。
- `descriptor.mod.example` 不直接覆盖玩家现有本地 Mod 描述文件。
- 测试生成物、游戏日志和临时二进制资产默认不进入 Git。

# 6. 原型通过顺序

原型必须按以下顺序逐层通过，失败时不得跳到下一层：

1. 独立测试舰能够由固定入口生成、跃迁、交战和被摧毁。
2. 国家账本只允许首次生成一个正式身份。
3. 真正摧毁能够触发一次且仅一次的首都满状态重现。
4. 紧急撤退、跃迁、失联和读档不会误触发重现。
5. 舰队合并、拆分、升级和重复入口不能生成第二个合法身份。
6. 部署锁定可以阻止离场，并在中断后保持幂等。
7. 爱缪莎参与条件能够在不改变领袖职业的情况下控制部署入口。
8. 新开局、战斗中存档、摧毁帧附近读档与迁都后摧毁均通过。

# 7. 性能预算

- 正常运行不得使用每月 `every_country`、`every_owned_fleet` 或全银河舰船扫描。
- 常驻状态只保存少量国家 flag、变量和必要对象标记。
- 一致性审计只在首次建造、确认摧毁、重现完成、明确读档恢复入口和开发命令中运行。
- 对象检索优先限定路线国家和正式身份标记，不把普通同级舰船纳入候选。
- 性能验收不仅记录平均帧率，还要检查月结尖峰、事件重复次数和存档体积变化。

# 9. TFR-001：隔离原型位置、命名空间与装载方式

## 9.1 方案 A：仓库外层测试骨架，手动组装临时 Mod（推荐）

- 原型源文件放在 `tools/prototypes/aemusa_flagship/mod_skeleton/`，不会被正式 Mod 加载。
- 测试时由明确的构建或复制步骤组装到独立临时 Mod 目录，不覆盖 `mod/descriptor.mod`。
- 使用独立 namespace 和统一前缀，例如 `aemusa_flagship_proto` 与 `aemusa_fp_*`；正式实现不得直接沿用测试 key。
- 只提供开发事件或控制台入口，不注册普通开局、月度脉冲或正式科技解锁。
- 测试报告和原型源文件可以进入 Git；本地临时 Mod、日志、存档和二进制生成物不进入 Git。

优势：原型默认完全不加载，最不容易污染正式 Mod、正式存档和现有舰船定义；失败时可整体删除。

风险：每次测试前需要执行一次明确的组装步骤，必须避免测试人员误把临时 Mod 当作正式版本发布。

## 9.2 方案 B：原型文件放入正式 Mod，但用隐藏触发器关闭

原型定义直接放入 `mod/`，正常情况下依靠永假触发器或调试 flag 隐藏。

优势：无需单独组装测试 Mod，修改后可直接启动游戏验证。

风险：即使事件不触发，舰船尺寸、设计、部件和本地化仍可能被加载；命名冲突、错误日志和发布污染风险较高。

## 9.3 方案 C：直接复用现有正式舰船脚本作为原型

在当前专属舰脚本上逐步加入账本、重现和独立编队逻辑。

优势：最快看到游戏内效果，也能复用现有舰船资源。

风险：旧舰名、旧模型、旧超规格槽位和历史兼容问题会混入验证结果，无法证明新职责本身是否可行，也违反已批准的隔离要求。

## 9.4 当前建议

建议批准方案 A。技术原型首先要保证“失败可以完整撤销”，其次才是启动方便。独立骨架还能强制我们为每个测试列出依赖，而不是继续依赖当前正式 Mod 中尚未清理的旧舰船实现。

## 9.5 审核结论

- 决定：批准方案 A“仓库外层测试骨架，手动组装临时 Mod”。
- 原型源文件位置锁定为 `tools/prototypes/aemusa_flagship/`，不得直接写入正式 `mod/`。
- 原型通过独立临时 Mod 装载，不覆盖正式 `descriptor.mod`，也不依赖正式舰船、科技、主线或美术资源。
- 原型统一使用 `aemusa_flagship_proto` namespace 与 `aemusa_fp_*` 测试前缀；正式实现不得直接沿用测试 key。
- 原型只提供明确的开发事件或控制台入口，不注册普通开局、月度脉冲或正式科技触发。
- 可提交 Git 的范围为原型源文件、说明、测试用例和报告；临时 Mod、存档、日志及二进制生成物不进入 Git。
- 本批准只确定隔离合同，不创建原型目录或脚本，隔离原型闸门继续关闭。
- 批准日期：2026-08-01。

# 10. TFR-002：生命周期账本到脚本状态的映射

本审核项决定国家、舰船和一次性事件分别保存什么状态。目标是让“同一永久身份”不依赖某一个会在摧毁时消失的舰船对象，同时避免多个 flag 互相矛盾。

## 10.1 方案 A：国家数值主状态＋永久里程碑＋舰船身份标记（推荐）

### 10.1.1 国家主状态

- 路线所属国家保存一个权威生命周期变量，原型暂用 `aemusa_fp_lifecycle`。
- 状态枚举建议为：
  - `0`：未解锁。
  - `10`：已解锁、可首次建造。
  - `20`：首次建造处理中。
  - `30`：正式旗舰现役。
  - `40`：已确认摧毁、等待本次重现处理。
  - `50`：重现事件处理中。
- 重现成功后回到 `30`；不额外设置一个长期“重现后现役”状态，避免现役被拆成多个等价分支。
- 任何状态变化都必须经过集中 scripted effect 或等价单一入口；普通事件不能任意改写变量。

### 10.1.2 永久里程碑

- 使用独立永久 country flag 记录“首次正式建造已经完成”，不能因舰船摧毁而清除。
- 使用单独变量保存最近一次确认摧毁序号和最近一次完成重现序号；二者相等表示当前摧毁已经处理。
- 主线阶段、原版天灾完成、旗舰建造资格和舰船生命周期分别记录，不把所有含义塞进同一个 flag。
- 奖励、通讯和教程节点使用各自的一次性里程碑，不能只根据现役舰船是否存在重复触发。

### 10.1.3 舰船与舰队对象标记

- 正式物质舰体保存一个 ship flag，表示它是当前永久身份的合法载体。
- 独立舰队可以保存辅助 fleet flag，用于 UI、合并审计和部署状态，但 fleet flag 不作为永久身份的唯一真相。
- 舰船和舰队对象被摧毁后可以消失；国家账本仍保留永久身份、摧毁序号和重现资格。
- 临时原型舰、旧测试舰、同舰种普通舰和视觉替代物不得携带正式身份标记。

### 10.1.4 一致性规则

- `lifecycle = 30` 时预期恰好存在一个合法 ship flag；找不到对象时先进入审计，不立即补舰。
- `lifecycle = 40` 且摧毁序号大于已处理序号时，允许进入一次重现处理。
- `lifecycle = 50` 时任何重复摧毁、读档恢复或调试入口都不得再次生成舰船。
- 重现舰生成并完成必需部件校验后，先记录已处理序号并切回 `30`，再显示通知。
- 若检测到两个合法对象，主线与奖励全部暂停，进入开发异常处理，不把两艘都当作现役。

优势：国家变量提供唯一权威状态，永久 flag 记录不可逆历史，舰船标记只确认当前载体；对象摧毁不会抹掉身份，也不会产生一组难以维护的互斥 flag。

风险：所有状态写入必须通过集中入口，否则数值状态与对象标记可能脱节；原型需要逐项测试非法跳转。

## 10.2 方案 B：每个阶段使用一个互斥 country flag

为未解锁、可建造、建造中、现役、摧毁和重现中分别设置 flag，切换时清除旧 flag、设置新 flag。

优势：脚本触发器直观，查看存档时容易辨认文字状态。

风险：事件中断后可能同时存在多个阶段 flag 或一个都没有；每增加状态都要修改所有清理分支，长期维护成本高。

## 10.3 方案 C：以保存的舰船或舰队 event target 为主状态

国家主要保存当前舰船或舰队 event target，通过目标是否存在判断现役与摧毁。

优势：能够直接定位当前对象，减少按标记搜索。

风险：舰船被摧毁后对象引用可能失效；仅凭引用不存在无法区分真正摧毁、撤退、隐藏和存读档边界，不适合作为永久身份账本。

## 10.4 当前建议

建议批准方案 A。永久身份属于国家级剧情账本，当前舰体只是该身份的载体。数值主状态负责互斥阶段，永久 flag 负责不可逆历史，ship/fleet flag 负责当前对象定位，三者职责分离最清楚。

## 10.5 审核结论

- 决定：批准方案 A“国家数值主状态＋永久里程碑＋舰船身份标记”。
- 路线国家使用一个权威生命周期变量，原型状态锁定为 `0/10/20/30/40/50` 六档；重现成功后从 `50` 返回 `30`。
- 首次正式建造完成使用独立永久 country flag 记录，摧毁时不得清除。
- 最近确认摧毁序号与最近完成重现序号分别保存；只有前者大于后者时才存在未处理摧毁。
- 正式物质舰体使用 ship flag 标识当前合法载体；独立舰队的 fleet flag 只用于辅助编队、部署和审计，不作为永久身份真相。
- 主线阶段、建造资格、生命周期、奖励和通讯各自保存状态，不把不同含义压进单个 flag。
- 所有主状态写入必须经过集中转换入口；禁止普通事件跨越合法状态或直接任意赋值。
- `30` 状态预期恰好存在一个合法舰体；`40` 允许处理一项未完成重现；`50` 阻止重入生成。
- 发现多个合法对象时暂停主线和奖励，进入异常审计，不把多个对象都视为正式旗舰。
- 本阶段只批准映射，不创建变量、flag 或 scripted effect 文件。
- 批准日期：2026-08-01。

# 11. TFR-003：摧毁识别与即时重现事件顺序

本审核项决定如何把舰船对象的真正摧毁安全转交给国家账本，再于首都生成新的物质载体。具体 Stellaris on_action 名称和可用作用域必须在原型编写前对照 4.4.3 原版文件验证，本蓝图不臆造回调 key。

## 11.1 方案 A：摧毁回调与国家重现处理器的两阶段事务（推荐）

### 11.1.1 第一阶段：确认摧毁并登记

1. 仅从经过原版文件确认的“舰船真正被摧毁”入口接收候选对象。
2. 在舰船与原所有者作用域仍可安全读取时，检查正式 ship flag、路线国家、`lifecycle = 30` 和首次建造里程碑。
3. 条件成立后，在国家账本中递增确认摧毁序号，并把生命周期从 `30` 转为 `40`。
4. 本阶段只登记一次，不生成奖励、不播放完整重现演出，也不依赖之后继续访问已销毁舰船对象。
5. 紧急撤退、失联、跃迁、事件隐藏、舰队解散或普通“对象暂时查询不到”不得调用本入口。

### 11.1.2 第二阶段：国家级重现事务

1. 由路线国家作用域的专用处理器接管，不继续把已销毁 ship/fleet 作为根作用域。
2. 再次检查：`lifecycle = 40`、摧毁序号大于已处理序号、没有现役合法舰体、路线国家仍存在且拥有合法首都。
3. 条件成立后先把生命周期切换到 `50`，形成重入锁。
4. 在当前合法首都对应的安全生成位置创建独立舰队，并按最后确认的合法玩家方案恢复舰体，立即写入合法 ship/fleet 标记。
5. 验证新舰体存在且必需核心设计已成功挂载后，写入已处理序号并把生命周期切回 `30`。
6. 只有账本完成后才播放一次重现通知、镜头或其他非关键演出。
7. 整个事务不重新发放首次建造奖励、危机研究、锚点进度或主线阶段奖励。

### 11.1.3 “立即”的技术定义

- 叙事与玩家体验上的“立即”表示不需要等待项目、资源、月结或长期计时器。
- 若原型证明同一回调帧生成会导致作用域、战斗结算或重复触发异常，允许在最短安全事件边界执行国家处理器。
- 这种引擎安全延后不得成为可见停用期，也不得改变满状态首都重现的批准结论。
- 具体是同一事件链、零日调度还是最短安全延迟，只能由隔离原型结果决定。

### 11.1.4 失败与恢复

- 若没有合法首都、合法设计解析失败、舰体创建失败或对象校验失败，不得把已处理序号推进到最新摧毁序号。
- 失败状态保留足够账本证据，由读档审计或开发恢复入口继续同一事务，不能新开第二个摧毁序号。
- 恢复过程中仍先检查是否已经存在合法舰体，避免“生成成功但最后一步记录失败”导致再次生成。
- 正常游戏不使用月度补舰；恢复触发点留给 `TFR-006` 审核。

优势：摧毁入口只负责把事实写入仍然存在的国家账本，生成入口在稳定的 country 作用域中完成；重入锁和序号可以阻止同一摧毁重复生舰。

风险：必须在原型中确认可用的真正摧毁入口及其作用域生命周期，并测试同帧或最短安全事件边界对战斗结算的影响。

## 11.2 方案 B：在舰船摧毁回调中直接生成替代舰

检测到正式舰体被摧毁后，立即在同一个舰船回调里查找首都、生成舰队、写入标记和播放通知。

优势：事件数量少，表面上最接近同一帧立即重现。

风险：过度依赖即将消失的 ship/fleet 作用域；生成新舰后可能重入同类逻辑，任何中途失败都难以判断账本已经执行到哪一步。

## 11.3 方案 C：不监听摧毁，只在对象缺失时重现

读档、界面、月结或其他入口发现 `lifecycle = 30` 但找不到旗舰，就把它当作已摧毁并生成替代舰。

优势：不依赖具体摧毁回调。

风险：会把撤退、跃迁、事件隐藏和查询延迟误判为摧毁；与已批准的“事件驱动、不做月度轮询”直接冲突。

## 11.4 当前建议

建议批准方案 A。先把摧毁事实提交到国家账本，再由国家级事务完成首都重现，是兼顾立即体验、对象作用域安全和幂等性的唯一稳健结构。

## 11.5 审核结论

- 决定：批准方案 A“摧毁回调与国家重现处理器的两阶段事务”。
- 第一阶段只从经原版 4.4.3 文件确认的真正摧毁入口接收对象，在 ship/owner 作用域失效前验证正式身份、递增摧毁序号并把国家生命周期从 `30` 转为 `40`。
- 第一阶段不直接生成舰船、不结算奖励，也不在后续继续依赖已销毁舰船对象。
- 第二阶段由 country 作用域专用处理器接管，复核待处理序号、合法舰体数量、国家与首都后，先将状态从 `40` 转为重入锁 `50`。
- 在首都创建独立舰队并按最后确认的合法玩家方案恢复舰体、写入身份标记；确认对象与必需部件有效后，再写入已处理序号并回到现役状态 `30`。
- 通知、镜头和非关键演出必须在账本提交成功后执行，不能先发奖励再设置防重复状态。
- “立即”表示无项目、资源、月结和可见计时；若同一帧不安全，允许使用原型验证出的最短安全事件边界，但不得形成玩家可感知停用期。
- 紧急撤退、失联、跃迁、事件隐藏和查询不到对象不得调用真正摧毁入口。
- 生成失败不推进已处理序号；恢复时先检查是否已有合法舰体，避免生成成功但记录失败后再次生成。
- 具体摧毁回调 key 和作用域在原型编写前继续以原版文件为准，不在本蓝图中臆造。
- 批准日期：2026-08-01。

# 12. TFR-004：独立编队、合并防护与玩家可调整设计

原版 4.4.3 核验显示：巨像与噬星者使用 `shipclass_military_special`，主宰使用 `shipclass_starbase`；舰种可声明 `is_designable`、`enable_default_design` 和若干 `required_component_set`。当前原版脚本中没有发现可直接写入舰种定义的通用 `can_merge = no` 字段，因此“独立编队”必须以原版特殊军舰行为为基线实测，不能依靠虚构字段。

## 12.1 已批准修订方案 A：军事特殊舰、受约束的玩家设计与原生独立编队验证

### 12.1.1 舰种与编队基线

- 原型建立全新测试舰种，优先以 `class = shipclass_military_special` 为基线，对照巨像和噬星者的实际编队行为。
- 原型通过国家事件在独立新舰队中创建唯一舰体，不通过普通船厂菜单批量生产。
- 舰体与舰队分别写入测试身份标记，国家账本仍是唯一性的权威来源。
- 测试玩家的合并、拆分、舰队管理器、增援、升级、重命名、紧急撤退和控制权变化操作。
- 若 `shipclass_military_special` 原生阻止与普通军舰合并，则把该行为记录为可行依据；若不能可靠阻止，则本项不通过，必须重新审核而不是暗加高频轮询纠正。

### 12.1.2 受约束的玩家设计

- 原型允许该军事特殊舰进入舰船设计器；原版巨像已证明 `shipclass_military_special` 与可编辑舰船方案可以共存，因此无需仅为开放设计器直接降级为普通军舰。
- 玩家可以调整武器、防御与允许范围内的辅助部件；舰种、区段结构、永久身份与生命周期账本不得因方案名称或部件变化而改变。
- 舰种必须通过 `required_component_set` 强制要求能源核心、超光速、推进、传感器、作战电脑与已批准的两个光环槽，任何合法方案都必须能够保存、跃迁和战斗。
- 原型使用最低限度占位区段和原版可用测试部件，只验证设计器兼容性、必需部件、升级、生成、跃迁和战斗，不验证正式火力或外观。
- 唯一身份不得依赖舰船设计名；玩家重命名、更新或保存新版本不能创建第二个正式旗舰身份。
- 原型必须专项验证多个同舰种方案并存时，事件能否确定“被摧毁舰体最后安装且已确认合法的方案”。如果 4.4.3 脚本接口无法可靠恢复该方案，不得随机挑选同舰种设计。

### 12.1.3 唯一建造与重现

- 技术原型的首次舰只只从单次开发入口生成，用于验证状态机；它不代表正式版本可以免费获得。
- 正式版本的国家级建造流程与测试入口分离，仍服从 `FSR-001` 的正式建造要求。
- 重现优先恢复被摧毁舰体最后安装且已确认合法的玩家方案；不得使用会在多个同舰种方案中任意选择的无约束随机恢复。
- 生成后立即检查舰种、设计、核心部件、ship flag、fleet flag 与国家所有者；任一失败都不得提交现役状态。
- 如果精确恢复最后安装方案在隔离原型中不可行，先测试限制为唯一合法玩家方案；仍不可行时，按本项批准条件回退方案 B，而不是静默恢复错误配置。

### 12.1.4 不采用的取巧方式

- 不通过极端 `fleet_slot_size` 人为挤满舰队指挥上限来假装禁止合并；这会污染海军容量、舰队力量和 UI。
- 不使用不存在或未经原版验证的 `can_merge` 类字段。
- 不依靠月度扫描把被合并的舰船不断拆出。
- 不复用旧 `destiny_lord` 舰种、旧区段、旧全局设计或旧 Stage 9 模型作为原型。

优势：复用原版巨像、噬星者一类特殊军舰的引擎行为，同时保留玩家配置旗舰武器、防御与辅助部件的权利；必需核心部件由舰种约束而不是人工提醒保证。

风险：`shipclass_military_special` 是否完全满足玩家可控、可跃迁、可交战且不可与普通舰队合并仍须实测；玩家存在多个方案时能否准确恢复最后安装方案也须实测。任一关键条件失败，就执行已批准的方案 B 回退，不用随机设计或高频轮询掩盖失败。

## 12.2 方案 B：普通军舰类别＋可设计方案＋脚本审计

把旗舰作为普通 `shipclass_military` 舰种并保留玩家设计器；当方案 A 无法兼容玩家改装、准确重现或独立编队时，才启用本方案，并通过身份检查与事件审计维护单舰编队。

优势：舰船设计、升级、部件选择和普通战斗行为兼容性较高。

风险：与独立编队、固定身份和不可复制要求冲突；缺少可靠的合并回调时只能依赖频繁审计，增加性能与异常风险。

## 12.3 方案 C：主宰式 `shipclass_starbase`

参考主宰，把旗舰实现为可移动的星基地级对象，使其天然保持特殊编队，并获得主宰式部分行为。

优势：大型唯一舰与独立对象表现成熟，可能更容易保持单独存在。

风险：会带入移动船厂、星基地 UI、维修、光环和战斗行为等非目标特性；专属舰不是第二艘主宰，技术债务可能大于收益。

## 12.4 审核结论

批准修订方案 A：以军事特殊舰为首选，允许玩家调整设计，并用必需部件集合保证方案合法。隔离原型必须验证设计器、精确重现和独立编队；若其中任一硬条件无法实现，则按用户批准条件回退方案 B。回退不改变永久唯一身份账本、单舰编队职责或首都立即重现规则。

- 批准日期：2026-08-01。

# 13. TFR-005：现场部署锁定、爱缪莎参与条件与天灾总局势

## 13.1 已批准扩展方案 A：逐锚专项工程＋旗舰部署状态＋国家级天灾总局势

### 13.1.1 双层职责

- 每个正式终局锚点仍通过独立的现场专项工程执行初次恒定或重新校准；旗舰必须实际位于目标宿主星系，不能由国家界面远程完成。
- 专属天灾另建立一个国家级总局势，用于展示危机主阶段、公开的终局收敛压力、已发现锚点、已恒定或已毁灭锚点、弱点解析进度以及旗舰与专属巨构状态。
- 总局势是全局信息与压力展示层，不是锚点对象、旗舰生命周期或危机主状态的权威账本；权威状态仍保存在既有国家状态机和对象账本中。
- 总局势不得代替逐锚专项工程，也不得通过普通月度推进直接生成锚点、舰队、旗舰、巨构或奖励。

### 13.1.2 现场工程启动条件

- 当前对象必须是路线国家唯一合法旗舰，且处于可执行任务的现役状态。
- 旗舰必须位于目标正式锚点宿主星系，并且没有执行另一项恒定或重新校准。
- 目标锚点必须处于允许恒定或补充稳定余量的合法生命周期状态。
- 爱缪莎必须仍属于路线国家、保持唯一角色身份，并处于可参与规则同步的状态；她不需要担任舰队司令、改变职业或永久登舰。
- 旗舰处于跃迁、紧急撤退、失能、摧毁待重现或重入锁时不能开始工程。

### 13.1.3 部署锁定

- 工程开始后，国家账本记录当前锚点与本次作业序号，旗舰进入明确的部署状态，爱缪莎获得对应的临时校准占用状态。
- 部署期间禁止旗舰主动离开宿主范围、启动跃迁、紧急撤退或开始另一项任务。
- 是否允许旗舰在原地继续自卫开火由隔离原型验证；优先目标是允许被动自卫但禁止主动移动追击，不能只靠叙事文本假定引擎行为。
- 同一时刻只允许一项旗舰现场工程和一项爱缪莎校准占用；职业切换、通讯、解雇或重复招募不得绕过唯一占用。

### 13.1.4 完成、中断与恢复

- 首次恒定完成后写入锚点稳定余量、访问记录和一次性剧情账本；重新校准只补充允许的稳定余量，不重复首次奖励。
- 旗舰真正摧毁、玩家主动取消、目标锚点进入不兼容状态或爱缪莎无法继续参与时，工程不得直接判定完成。
- 旗舰摧毁后按已批准规则在首都立即重现，但必须重新返回目标星系继续未完成的现场作业。
- 读档恢复以危机状态机、专项工程序号、锚点生命周期、旗舰生命周期和爱缪莎占用状态交叉核验；总局势只重新读取这些事实，不反向制造缺失对象。

### 13.1.5 天灾总局势的性能边界

- 总局势只在已批准的专属天灾生命周期内存在或保持可见，不为每个锚点各创建一条长期国家局势。
- 局势显示数据由危机阶段转换、锚点结果、弱点解析和资产状态变化时主动刷新；不得用高频全银河扫描维持界面。
- 月度检查只能做低成本一致性校验和显示修复，不能成为危机推进、锚点生成或旗舰补发的正常入口。
- 专属天灾结束后，总局势进入已解决或战后结算状态；不得因读档、界面重开或残余投影再次初始化。

## 13.2 审核结论

- 决定：批准在方案 A 的逐锚现场专项工程基础上增加一条国家级专属天灾总局势。
- 专项工程负责具体锚点的现场恒定和重新校准；总局势负责全局阶段、压力和公开进度展示，两者不能相互替代。
- 爱缪莎继续作为独立领袖参与每次关键校准，不转为舰船组件或舰队司令。
- 隔离原型必须验证部署期间的移动、跃迁、撤退、自卫开火、工程中断和读档恢复行为。
- 具体局势界面文案、阶段图标、数值刻度和刷新事件留待后续 UI 与实现审核；本项不开放正式代码实现。
- 批准日期：2026-08-01。

# 14. TFR-006：存读档故障注入、迁都与性能测试

## 14.1 已批准方案 A：完整状态矩阵与主动故障注入

### 14.1.1 存读档状态矩阵

隔离原型必须至少在以下节点分别保存、退出、重新加载并继续验证：

- 尚未取得首次建造资格。
- 已取得资格但尚未建造。
- 首次建造事务进行中。
- 旗舰正常现役。
- 旗舰正在跃迁或处于紧急撤退识别窗口。
- 旗舰正在现场恒定或重新校准。
- 旗舰刚被确认摧毁、国家账本处于待处理状态 `40`。
- 重现事务已经进入重入锁状态 `50`，但新舰体尚未通过验证。
- 新舰体已经生成，但已处理序号和尚未最终提交。
- 重现事务成功完成并回到现役状态 `30`。
- 专属天灾总局势正在推进、阶段刚切换或刚完成。

每个节点都检查生命周期、摧毁序号、已处理序号、首次建造永久标记、合法舰体数量、舰队标记、玩家方案、部署目标、爱缪莎占用、天灾总局势和锚点账本是否保持一致。

### 14.1.2 主动故障注入

- 对同一次摧毁重复发送回调，验证只产生一次待处理事务和一次重现。
- 对同一待处理序号重复调用重现处理器，验证重入锁和已处理序号阻止第二艘舰体。
- 删除舰体但不写摧毁记录，验证系统进入异常审计而不是立即补舰。
- 写入摧毁记录但保留原舰，验证处理器先发现已有合法对象并拒绝复制。
- 人工制造第二艘带正式 ship flag 的舰体，验证多对象异常暂停主线、奖励和自动修复。
- 生成同舰种但没有正式身份的测试舰，验证它不会被纳入旗舰生命周期。
- 尝试合并、拆分、增援、升级、改名和舰队管理器操作，验证独立编队与身份不被破坏。
- 同时保存多个玩家方案，删除或替换最后安装方案，验证重现不会无约束随机选择错误设计。
- 在部署期间强制跃迁、撤退、切换任务、摧毁旗舰或中断爱缪莎参与，验证专项工程不被错误完成。
- 让旧阶段延时事件在新阶段到达，验证状态和序号不匹配时静默失效。

### 14.1.3 迁都与国家边界

- 旗舰正常现役时迁都不移动、复制或重建现有舰体。
- 摧毁前已经迁都时，在新首都对应的合法位置重现。
- 摧毁记录后、重现提交前发生迁都时，以重现处理时的当前合法首都为准。
- 没有合法首都时进入明确阻塞状态，不生成到随机星系、旧首都、盟友或其他国家。
- 合法首都恢复后只恢复同一个待处理事务，并且最多生成一次。
- 路线国家彻底灭亡时不把旗舰转交其他国家；1.0 暂不处理多人继承。

### 14.1.4 性能基线

- 正常流程不得使用月度全银河扫描补舰，也不得遍历所有同级舰船判断旗舰是否存在。
- 专属天灾总局势由危机阶段、锚点结果、弱点解析与资产状态变化主动刷新。
- 必要的一致性检查只读取路线国家账本、已保存目标和带正式标记的候选对象。
- 分别测量无旗舰、旗舰现役、旗舰部署、旗舰待重现与专属天灾进行中的事件调用次数、重复回调、月结尖峰和存档体积变化。
- 开发审计日志必须可以关闭；正式实现不得持续输出高频状态日志。
- 性能报告必须记录测试时长、游戏速度、存档阶段、启用 Mod 范围和观察到的尖峰，不能只写“感觉正常”。

### 14.1.5 通过标准

- 任意测试节点最多存在一艘合法旗舰；异常制造的多对象不会推进主线或结算奖励。
- 同一次确认摧毁最多执行一次首都重现。
- 首次建造、剧情、奖励、局势与锚点结果不会因读档或重复回调再次执行。
- 迁都不会复制或永久丢失旗舰；无首都阻塞能够在恢复合法首都后幂等继续。
- 普通月结、科技刷新、界面重开和舰队管理操作不会生成旗舰。
- 没有持续全银河扫描、失控事件循环或可归因于原型的明显月结尖峰。

## 14.2 审核结论

- 决定：批准方案 A“完整状态矩阵与主动故障注入”。
- 存读档、事务中断、重复回调、多舰体、多方案、部署中断、迁都、无首都和旧回调全部属于隔离原型的硬性测试范围。
- 性能验收必须提供可复核的数据与日志摘要，不以主观流畅度代替。
- 本项只批准测试计划，不创建原型代码，也不修改正式 Mod。
- 批准日期：2026-08-01。
