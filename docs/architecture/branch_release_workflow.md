# 分支与发布工作流

## 1. 长期分支职责

| 分支 | 职责 | 允许内容 |
| --- | --- | --- |
| `main` | 已通过测试的稳定版本 | 只接受完成验收的快进合并或发布修复 |
| `parallel/v1-integration` | v0.1.0 封版候选 | 只接受 v0.1 阻断修复和测试报告更新 |
| `refactor/v0.2-architecture` | v0.2 架构准备 | 文档、验证工具、无玩法迁移 |
| `feature/<name>` | 单一功能 | 一个明确模块，不跨文件所有权 |
| `fix/<name>` | 单一错误 | 最小修复和回归测试 |
| `art/<name>` | 美术与模型 | 源资产、导出物和接入脚本分开提交 |

## 2. 当前并行关系

```text
main
  └─ parallel/v1-integration  → v0.1.0 游戏内复测 → main → tag v0.1.0
       └─ refactor/v0.2-architecture → v0.1.0 发布后再同步稳定基线
```

v0.2 架构分支不得反向合并到 v0.1 候选。若 v0.1 复测产生修复，应先进入 `parallel/v1-integration`，发布后再把对应提交同步到 v0.2 分支。

## 3. 提交规范

提交信息使用中文，采用以下动词：

- `修复`：错误或兼容性修复。
- `整理`：不改变行为的文件或文档整理。
- `拆分`：模块物理拆分且公共 ID 不变。
- `新增`：新功能或新内容。
- `更新`：状态、报告或依赖信息。

一个提交只解决一个主题。提交说明至少记录：

- 改动模块。
- 主要文件。
- 是否改变公共 ID。
- 静态检查结果。
- 游戏内测试结果。

## 4. 合并门槛

### 文档与工具分支

- 工作区干净。
- 静态验证工具自身可运行。
- `mod/` 与基线无差异，或差异经过明确批准。
- 文档没有互相冲突的版本与组织定位。

### 功能分支

- 静态验证通过。
- 新开局测试通过。
- 涉及持久状态时完成读档测试。
- 涉及旧 key 时完成旧存档测试。
- `error.log` 没有本模块新增硬错误。

## 5. 发布流程

1. 冻结发布范围。
2. 创建候选提交并推送集成分支。
3. 只启用本 Mod 完成手动测试。
4. 回写测试报告和已知问题。
5. 快进合并到 `main`。
6. 创建附注版本标签。
7. 推送 `main` 和标签。
8. 从正式标签继续后续版本开发。

禁止在未完成游戏内测试时提前创建正式标签。
