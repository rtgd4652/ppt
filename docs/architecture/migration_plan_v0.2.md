# v0.2 架构迁移计划

## 1. 迁移原则

- v0.1.0 正式发布前不移动运行定义。
- 一次只迁移一个模块。
- 迁移提交不修改玩法和数值。
- 每次迁移前后比较 `mod/` 对象 key、事件 ID 和本地化 key。
- 每个阶段都必须可以单独回退。

## 2. Phase 0：架构基线

状态：本分支执行。

- 建立架构文档。
- 建立静态验证工具。
- 建立模块所有权和稳定 ID 规范。
- 不修改 `mod/` 运行内容。

验收：与 `parallel/v1-integration` 比较时，`mod/` 无差异。

## 3. Phase 1：本地化拆分

优先级：高，风险：低。

迁移顺序：

1. core。
2. white_night。
3. leaders。
4. economy。
5. progression。
6. destiny content。

规则：

- 每个 key 只移动，不改名、不改文本。
- 每迁移一个模块就运行重复 key 检查。
- 所有简体中文文件保留 UTF-8 BOM。

验收：新开局本地化与迁移前完全一致，不出现内部 key。

## 4. Phase 2：角色 scripted effect 拆分

优先级：高，风险：中。

- 从 `aemusa_leader_effects.txt` 依次移出赛斯、幽桐、拉比。
- 爱缪莎逻辑最后迁移。
- 保留全部现有效果名称和 flag。
- 新角色安托涅瓦、晏华直接使用新结构。

验收：四名现有角色的创建结果、职业、trait、等级和唯一性与迁移前一致。

## 5. Phase 3：白夜馆事件拆分

优先级：高，风险：中高。

- 先保留 `aemusa_dialogue` 的旧事件 ID。
- 将白夜馆主菜单定义为路由层。
- 新角色使用独立 namespace。
- 旧角色事件只有在验证相同 namespace 可跨文件稳定加载后才物理拆分。

验收：白夜馆反复进入、返回、招募和读档不产生重复领袖或丢失入口。

## 6. Phase 4：on_action 集成

优先级：中，风险：高。

- 保留单一 `aemod_on_actions.txt`。
- on_action 只转发模块事件，不写长业务逻辑。
- 每个转发事件自行检查最小触发条件。
- 月度逻辑必须有明确 flag，禁止无条件重复扫描全银河。

验收：升级、开局、舰船摧毁和存读档触发次数符合预期。

## 7. Phase 5：经济与成长模块

优先级：中，风险：中。

- 建筑、区划和岗位保持独立文件所有权。
- 科技、传统和飞升统一由 progression 管理解锁关系。
- 本阶段只整理依赖，不同时调整数值。

验收：科技抽取、区划建造、岗位月结、传统和飞升均与迁移前一致。

## 8. Phase 6：舰船与巨构

优先级：后置，风险：高。

- 命运之主组件、舰体、区段、设计和事件分别明确所有权。
- 模型 locator 完成前不恢复武器槽。
- 命运观测塔模型、动画和 LOD 单独测试后再接入脚本。
- 美术风格确定后再集中补图标。

验收：舰船可建造、跃迁、重构；巨构可完成所有阶段并切换政策。

## 9. 每阶段检查清单

- [ ] 没有改变公共 key。
- [ ] 没有重复事件 ID。
- [ ] 没有重复本地化 key。
- [ ] 非本地化脚本无 BOM。
- [ ] 简体中文本地化保留 BOM。
- [ ] 静态验证通过。
- [ ] 新开局通过。
- [ ] 指定旧存档通过。
- [ ] `error.log` 没有本模块新增硬错误。
- [ ] 提交信息说明迁移范围和测试结果。
