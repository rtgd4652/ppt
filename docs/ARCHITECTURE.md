# 项目架构与变更边界

更新：2026-10-09。本文记录工程职责；叙事与世界观以已有人工批准材料为准。当前进度见 [PROJECT_STATUS](PROJECT_STATUS.md)。

## 数据与生产流

```text
raw + indexes → knowledge 清洗／人工审核／项目正史 → docs 设计与工作包
                                                       ↓
assets 制作源文件 → 已验收运行资源 ───────────────────→ mod
                                                       ↓
tools 检查与构建 ───────────────────────────────────→ reports 验收证据
```

- 来源采集不直接改变项目正史；SQLite 由 Markdown、JSON 与来源文件重建。
- 设计文档不能自动修改运行状态或提升审核状态。
- `mod/` 是唯一运行根目录；其内部保留 Stellaris 所需目录，不为管理便利搬成引擎不识别的结构。
- `art/` 与开发素材不自动进入发布包；工具、缓存、原型与正式资产分开管理。

## 运行模块

| 模块 | 当前落点 | 负责 | 边界 |
| --- | --- | --- | --- |
| 文明底座 | `mod/common/` 的物种、起源、科技、传统、建筑、岗位等 | 开局与文明成长 | 不写主线终局事实 |
| 白夜馆 | `aemusa_dialogue_events.txt`、法令与界面声明 | 招募、通讯、档案、主线入口 | 读取主线合法入口，不持有唯一进度 |
| 角色 | 领袖 effects、traits、portraits 与角色事件 | 唯一人物、职业、成长、个人机制 | 不共用他人的机制阶段或冷却 |
| 成长基准 | `artifact_growth_effects.txt`与名册事件／本地化 | 从实际所有人物与基础等级派生成长阶段及项目基准 | 只重算派生值，不写经验／核心记录；各项目持有参与资格与实际贡献 |
| 协作工程 | `artifact_engineering_events.txt`及同名前缀effects／triggers／修正 | 实际目标、投入、参与者、月度工作及一次性研究成果 | 只读取角色资格并持有参与占用，不重置个人核心，不写主线转变事实；乘算限定本项目 |
| 主线编排 | `aemusa_main_story_events.txt`、分包事件文件 | 章节顺序、暂停、恢复、选择 | 不代替外部战争／天灾制造胜利 |
| 状态接口 | `aemusa_ms_story_entry_triggers.txt`、`aemusa_ms_story_lifecycle_effects.txt` | 只读前置、受控写入、一次性结算 | 历史事实持久化；不依据窗口是否打开推断完成 |
| 外部适配 | `on_actions` 及未来独立适配模块 | 记录真实游戏行动与已结算结果 | 回传最小事实，不越级推进章节 |
| 审计 | `aemusa_ms_state_audit_*` 与包级日志 | 发现非法状态并输出证据 | 不自动补齐玩家选择、胜利或终局身份 |

更细的契约继续使用 [现有接口设计](design/aemusa_main_story_implementation_interface_v1.0.md)。本次不重写已经通过验证的状态机。

## 后续文件拆分规则

1. 新章节使用独立事件文件，白夜馆只增加对应路由。
2. 新角色的招募／通讯／机制逐步拆分；共用唯一性与职业处理通过已有或经验证的接口复用。
3. 本地化随新增模块拆分文件，避免把所有角色与章节继续堆进同一文件。
4. 移动既有定义时保持事件 ID、namespace、本地化 key 和存档状态 key 不变；不得留下重复定义。
5. 状态结构变化单独提出迁移方案，不能用重置、删除领袖再重建或猜测历史维持表面兼容。
6. 旧舰、旧塔保留遗留身份；新主线不能引用旧方案获得正式终局职责。

本次只清理失效图片声明。事件与本地化的渐进拆分在对应角色／章节实际修改时进行，避免无业务收益的大规模移动。

## 权威入口

README 只提供导航；旧规划保留历史标记。遇到冲突先查看具体范围与审核记录，不能简单以最新日期覆盖全部旧约束。

## 验证与交付

- 运行 `python -B tools/validation/check_mod.py`，检查结构、编码、项目事件／本地化／接口／状态与显式资源路径。
- 对改动涉及的机制执行定向游戏测试，记录 Git 提交或快照、游戏版本、存档和日志。
- 测试数据、只读审计与正常玩家流程分开；控制台注入不能作为正常流程通过证据。
- 每包交付包含入口、文本、必要表现与读档检查；最终全线回归继续保留。
- 当前混合工作区优先保存快照并核对归属，再按范围提交。快照恢复依赖记录的 base_commit，不能称为独立发行包。
